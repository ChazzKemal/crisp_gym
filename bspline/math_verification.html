The Windowing
Theorem

The claim the whole action representation rests on is that a slice of a spline is still that spline. This is the audit: each mathematical claim stated, derived, and then checked against something that shares no code with the thing being tested.

—

    00Method

    What counts as verification here

    A test that checks an implementation against itself proves nothing. Every claim below is measured against an independent reference.

    • A Cox–de Boor recursion written from the definition — nine lines, no library, used to confirm the basis functions really are non-negative, locally supported, and a partition of unity on the knot vectors we actually build.
    • scipy — interpolate.BSpline for evaluation, spatial.transform.Rotation for the rotation algebra.
    • node — the walkthrough page's own JavaScript decoder, extracted from its source and run against scipy's answers, so the explainer and the pipeline cannot drift.
    • Real recorded data — not synthetic fixtures. Splines fitted to the shortest twelve episodes of merged_act_finetune_20260528.

    Thresholds are stated per check. Where a claim is exact — a counting identity, an encoding round trip — the threshold is literally zero rather than a small epsilon.

    01Fundamentals

    Do our objects satisfy the axioms?

    Before trusting anything built on top, confirm that what generate_knots and make_lsq_spline hand back is a well-formed B-spline.

    Cox–de Boor recursion Bi,0(x) = 1 if ti ≤ x < ti+1, else 0
    Bi,k(x) = (x−ti) / (ti+k−ti) · Bi,k−1(x)  +  (ti+k+1−x) / (ti+k+1−ti+1) · Bi+1,k−1(x)

    Three properties follow from it and are worth confirming on our own knot vectors, because a degenerate fit (repeated knots, an empty span) can quietly break them: the basis is non-negative, each Bi,k is zero outside [ti, ti+k+1), and the basis sums to one across the domain. The support property is the one everything else depends on.

    02The central claim

    A window of a spline is that spline

    Chunking takes M = chunk + 2k consecutive knots and the control points carrying the same indices. The claim is that this reproduces the global curve exactly — no refit, no approximation.

    Statement Let S(x) = Σi ci Bi,kt(x), and set t′ = t[s : s+M], c′ = c[s : s+M−k−1].
    Then S′(x) = S(x) for every x ∈ [ts+k, ts+M−k−1).

    Why. Bj,kt′ depends only on the knots t′[j … j+k+1], which are exactly t[s+j … s+j+k+1]. So the windowed basis is the global basis re-indexed: Bj,kt′ = Bs+j,kt.

    For x in the span [tm, tm+1), only the k+1 basis functions with indices m−k … m are non-zero. The left end of the window gives x ≥ ts+k ⇒ m ≥ s+k ⇒ m−k ≥ s. The right end gives x < ts+M−k−1 ⇒ m ≤ s+M−k−2.

    Every active index therefore lies in [s, s+M−k−2], and all of those coefficients are present in c′. The two sums have identical terms. □

    This is also where the odd-looking slice in the decoder comes from. A knot vector of length M at degree k admits exactly M−k−1 control points, and params[:-(degree+1)] takes precisely that many — 22 rows of our 26.

    03Time origin

    Why subtracting the frame index is free

    Every stored chunk has its current frame subtracted from the knot column, so knots read as time-from-now. That has to leave the curve itself untouched.

    Why. By induction on k. At k = 0 the condition ti−c ≤ x−c < ti+1−c is the same inequality as before the shift. For the step, every coefficient in the recursion is a ratio of differences — (x−ti) / (ti+k−ti) — and a common c cancels from numerator and denominator alike. So Bi,kt−c(x−c) = Bi,kt(x). □

    Checked at shifts of 0, 1, 7, −13 and 137.5 frames — including a shift larger than the whole chunk and a fractional one, since nothing in the argument requires an integer.

    04Encoding

    The relative-knot form is a bijection

    The optional encoding replaces the knot column with its first valid entry followed by adjacent differences. If it is to be an alternative representation rather than a lossy one, it has to invert exactly.

    Encode / decode encode: e0 = tk,   ei = ti − ti−1 for i ≥ 1
    decode: tk = e0, then walk down with ti = ti+1 − ei+1 and up with ti = ti−1 + ei

    Decoding recovers tk directly, then every other knot by telescoping the differences from it in both directions — so the map is injective and its inverse is the one implemented. Worth keeping honest because this encoding is the natural fix for the knot column's fragility: it turns "the knots must come out ordered" into "the predicted differences must come out non-negative".

    05Evaluators

    Four implementations, one answer

    The same spline gets evaluated by scipy during conversion, by de Boor's algorithm in the browser, and — here — by a direct sum over basis functions. All three must agree to floating-point precision, or one of them is lying.

    The JavaScript case matters most. The walkthrough page reimplements findSpan and evalSpline so it can decode chunks live rather than ship pre-rendered images. Those functions are extracted from the page's own source, run under node against scipy's answers on real chunks, and compared. If someone edits the page's maths, this check fails.

    06The degeneracy

    Where the last waypoint goes

    A chunk running past the end of the knot vector is padded by repeating the final knot. The last decoded waypoint of such a chunk collapses to the origin — and there is a precise reason, not a numerical accident.

    Basis functions have half-open support: Bi,k is supported on [ti, ti+k+1), closed on the left and open on the right. When the tail is padded, every knot from tM−k−1 onward equals tmax, so at exactly x = tmax every remaining basis function has already closed.

    The sharp way to say it: partition of unity fails at that one point. The basis sums to 0 there instead of 1, so the curve evaluates to 0 regardless of the control points. On an interior chunk the same point is perfectly well behaved, because its tmax is strictly below the next knot. The decoder drops the final sample of a padded chunk; it only ever occurs at the end of an episode.

    07Rotation

    Replacing pytorch3d without changing conventions

    Upstream converts rotations through pytorch3d. We reimplemented the two maps in numpy to avoid a heavy pinned dependency — which is only safe if the conventions match exactly, including which two rows of the matrix become the 6D vector.

    The 6D continuous representation (Zhou et al.) forward: R → (R0·, R1·) — the first two rows, flattened
    inverse: b1 = norm(a1),   b2 = norm(a2 − (b1·a2)b1),   b3 = b1 × b2

    Rows, not columns — getting that backwards yields the transpose, which is still a valid rotation and so fails silently. The check compares against the matrix entries directly with a threshold of exactly zero.

    Gram–Schmidt also does real work at deployment: a network's six output numbers are not orthonormal, and this map projects any six numbers onto SO(3). That is checked with heavy noise added, verifying RRT = I and det R = +1 rather than just that it returns something.

    08Pipeline

    The parts that are ours, not the maths

    Three claims about the code around the spline: the fit honours its tolerance, the frame→chunk assignment does what it says, and the normalisation is invertible.

    The assignment check is the interesting one. The sampler assigns chunks with an imperative loop carried over from upstream — a running index advanced by a while inside a for. That is easy to port subtly wrong, so it is verified against an independently derived closed form: frame i takes the smallest window s with ts+k ≥ i. Agreement is required on every frame of every fitted episode, not a sample.

    09Normalisation

    One scale per column

    Upstream's normaliser collapses the step axis before computing statistics, so all 26 rows of a column share one scale. That is deliberate, and worth stating.

    Normalising each row independently would destroy the knot column's meaning: monotonicity is a relation between rows, and it only survives into the network's output space if the rows share an origin and a scale. The converted dataset's statistics are written this way and the check confirms they really are constant down every column.

    10Limits

    What this does not prove

    Everything above concerns whether the implementation computes what the mathematics says. It is silent on whether the mathematics is the right choice.

    Out of scope

    Optimality of the fit. generate_knots grows a knot vector greedily and stops at the first one inside tolerance. Nothing here claims that is the fewest knots possible, only that the result meets the tolerance it promised.

    Whether 0.01 is the right tolerance. That was chosen by measurement, not proof — the sweep is in the walkthrough. A different task might want a different point on that curve.

    Policy accuracy. Whether a trained network predicts good parameters is an empirical question, handled by eval_bspline_checkpoint.py. These checks would all pass on an untrained model.

    The knot column's fragility. The measured failure mode — a small fraction of predicted knot pairs coming out non-monotone, repaired by safer_knots — is a property of the training setup, not of the maths. Section 04 verifies that the relative-knot encoding is available and exact; it does not claim that switching to it helps.
